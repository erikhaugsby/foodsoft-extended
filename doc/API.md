# Foodsoft API

Foodsoft provides a JSON REST API that gives access to operations like
like listing open orders, updating the ordergroup's order, and listing financial
transactions. Not all Foodsoft functionality is available through the API, but
we're open for new additions.

The API is documented using [Open API 3.0.1](https://github.com/OAI/OpenAPI-Specification)
/ [Swagger](https://swagger.io/) in [swagger.yaml](/swagger/v1/swagger.yaml).
This provides a machine-readable reference that is used to provide documentation.
It is generated by [rswag](https://github.com/rswag) wich also provides api-tests.
It can be generated running `RAILS_ENV=test rails rswag`.

**Note:** the current OAuth scopes may be subject to change, until the next release of Foodsoft.

## API endpoint documentation

&gt;&gt; [View API documentation](http://petstore.swagger.io/?url=https%3A%2F%2Fraw.githubusercontent.com%2Ffoodcoops%2Ffoodsoft%2Fmaster%2Fdoc%2Fswagger.v1.yml) &lt;&lt;

The above documentation can communicate with the API directly on a local development
installation of Foodsoft at [http://localhost:3000/f](http://localhost:3000/f).

You'll need to give access to the application first. This can be done by going to
_Administration_ > _Configuration_ > _Apps_ in Foodsoft. Select _New Application_,
enter any name, put `http://petstore.swagger.io/oauth2-redirect.html` in _Redirect URI_
and disable _Confidential_. After submission, you will have an _Application UID_ that
you can enter that as `client_id` after clicking _Authorize_ in the Swagger UI.


## Security

Uses the [Doorkeeper](https://github.com/doorkeeper-gem/doorkeeper) gem,
which provides an OAuth2 provider.


### Authorization code flow

This is the recommended flow for server-side web applications, where
members login with Foodsoft, then redirected to the app, which then obtains
an access token using the authorization code supplied at redirection.

Before you can obtain an access token, the client needs to obtain an id and secret.
(You can currently skip this for the password credentials flow.) This needs to be
done for each Foodsoft scope by an admin.

1. Click on the _Apps_ button at the right in Foodsoft's configuration screen.
2. Click on _New application_
3. Enter any _Name_ and put the website of your app in _Redirect URI_ and _Submit_.
4. Click on the new applications' name for the app id and secret.
5. To quickly test, logging into the app, press _Authorize_.

Note that the user doesn't need to confirm that he is giving the app access to his
Foodsoft account by default, since apps can only be created by admins. If you
want to change that, see disable `skip_authorization` in `config/initializers/doorkeeper.rb`.

[Read more](https://github.com/doorkeeper-gem/doorkeeper/wiki/Authorization-Code-Flow).


### Implicit flow

This is the recommended flow for client-side web applications. It looks a lot
like the authorization code flow, but when redirecting back to the app, the
access token is available directly as part of the url _fragment_ (`window.location.hash`).

This flow also needs to be registered in Foodsoft as in the authorization code flow,
but with _Confidential_ disabled. You only need the `client_id`, not the secret.

**note** please make sure you understand sections
[4.4.2](http://tools.ietf.org/html/rfc6819#section-4.4.2) and
[4.4.3](http://tools.ietf.org/html/rfc6819#section-4.4.3) of the OAuth2 Threat
Model document before using this flow.

You may find Doorkeeper's [implicit_grant_test](https://github.com/doorkeeper-gem/doorkeeper/blob/master/spec/requests/flows/implicit_grant_spec.rb) useful.


### Password credentials flow

To obtain a token using a username/password directly, you can do this:

```ruby
require 'oauth2'
c = OAuth2::Client.new('client_id', 'secret', site: 'http://localhost:3002/f/', authorize_url: 'oauth/authorize', token_url: 'oauth/token')
c.password.get_token('admin', 'secret').token
# => "1234567890abcdef1234567890abcdef1234567890abcdef123456790abcdef1"
```

Now use this token as value for the `access_token` when accessing the API, like
http://localhost:3002/f/api/v1/financial_transactions/1?access_token=12345...

[Read more](https://github.com/doorkeeper-gem/doorkeeper/wiki/Client-Credentials-flow).


## Logout

When the user logs out of Foodsoft, all access tokens are destroyed, except when
the token's scope includes `offline_access` (so offline applications are possible).


## Messages

Available when the messages plugin is enabled (otherwise every endpoint answers
`404`). Scopes: `messages:read` to read, `messages:write` to read, send, edit and
delete. Any member may use them; which messages a user sees follows the website
(public messages, plus private ones the user sent or received).

| Endpoint | What it does |
|---|---|
| `GET /api/v1/messages` | Readable messages, newest first, without deleted ones. `threads=true` lists only the first message of each thread (deleted ones included). Paginated with `page` and `per_page`. |
| `GET /api/v1/messages/{id}` | One message, with its recipients. |
| `GET /api/v1/messages/{id}/thread` | All readable messages of the thread, oldest first, including deleted ones as placeholders. |
| `GET /api/v1/messages/recipients?q=...` | Users and groups (workgroups, ordergroups, message groups) whose name matches, at least 2 characters. |
| `POST /api/v1/messages` | Sends a message, see below. |
| `PATCH /api/v1/messages/{id}` | Sender only: changes `subject` and/or `body`, sets `edited_at`. |
| `DELETE /api/v1/messages/{id}` | Sender or admin: removes the text and marks the message deleted; the subject stays as thread title. Answers `204`. |

Body for `POST` (wrapped in `message`):

- `send_method`: `recipients` (default), `all`, `workgroup`, `ordergroup`,
  `messagegroup` or `order`. `all` is refused when a mailing list is configured,
  as on the website.
- `recipient_ids`, `group_id` (for the three group methods), `order_id` (for `order`).
- `subject`, `body` (plain text; line breaks are kept), `private`.
- `reply_to`: id of a readable message. The reply goes to the original sender
  (and group), into the same thread, with the original's privacy and a "Re:"
  subject unless given.

`body` is returned as plain text, `body_html` as HTML; both are `null` for
deleted messages. `can_edit` and `can_delete` tell the app which buttons to show.
`for_me` is true when the message was addressed to the current user (directly,
through a group, to all members or to an order's members): exactly the people
Foodsoft emails it to. `GET /api/v1/messages?for_me=true` lists only those.

Every message is also emailed to recipients who receive email. Editing or
deleting a message changes it in Foodsoft only; emails that were already sent
stay as they were. A message deleted before its email job runs is not emailed.

## Managing orders, articles and invoices

Besides the member functions, the API offers a number of endpoints for members
with a role in the foodcoop. They need an access token with one of the optional
scopes below, _and_ the user needs the matching role.

| Scope | Role | Endpoints |
|---|---|---|
| `orders:write` | orders | `POST /orders`, `PATCH /orders/{id}`, `POST /orders/{id}/finish` |
| `orders:read` | orders or pickups | `GET /orders/{id}/documents/{document}` (PDF; `groups`, `articles`, `fax` or `matrix`) |
| `articles:read`, `articles:write` | article meta | `GET/POST /articles`, `GET/PATCH/DELETE /articles/{id}` |
| `invoices:read`, `invoices:write` | finance or invoices | `GET/POST /invoices`, `GET/PATCH /invoices/{id}`, `POST /invoices/{id}/attachments`, `GET/DELETE /invoices/{id}/attachments/{attachment_id}` |
| `suppliers:read` (or any of the write scopes above) | any of the roles above | `GET /suppliers`, `GET /suppliers/{id}` |

Request bodies are JSON objects wrapped in the resource name, for example
`{"order": {"supplier_id": 3, "ends": "2024-05-10T18:00:00+02:00"}}`.

* Opening an order without `article_ids` offers all available articles of the supplier.
  Stock orders cannot be opened through the API yet.
* `POST /orders/{id}/finish` closes an open order for ordering. Settling (accounting) is
  not part of the API.
* `DELETE /articles/{id}` marks the article as deleted; this is refused while the article
  is part of an open order.
* Files (JPEG, PNG or PDF, e.g. a photo of a receipt) are uploaded as `multipart/form-data`
  in the field `attachments[]`, either together with the invoice fields on
  `POST /invoices`, or later on `POST /invoices/{id}/attachments`.
* As in the web interface, members with only the invoices role can change their own unpaid
  invoices, and `paid_on` can only be set with the finance role.


## Links

`GET /api/v1/links` (scope `config:user`, any member): the coop's links from the
website's "Links" menu that the member may open (links without a workgroup, links
of the member's workgroups, all for admins), ordered by name, as
`{"links": [{"id": 1, "name": "Webmail"}]}`. Addresses and credentials are not
included; apps open `/links/{id}` in their web view, where the website does the
rest. 404 when the links plugin is not installed.

## Orders: extra fields

Order JSON also has `invoice_id` (the linked invoice, or null) and
`supplier_min_order_quantity` (the supplier's minimum order as free text, e.g.
"50 EUR"), which every member may see, as on the website's ordering page.
